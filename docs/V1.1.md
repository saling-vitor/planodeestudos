# Plano ARQ · Ciclo V1.1

Documento operacional do ciclo posterior à V1.0.0.

## Baseline congelada

- Base aprovada da V1.0.0: `6249beebee753a5e51ed879fb8b7de924dee1a48`.
- Branch congelada: `release/v1.0.0`.
- `main` permanece nessa mesma baseline enquanto a V1.0.0 não receber tag/release oficial no GitHub.
- A tag `v1.0.0` e o GitHub Release ainda precisam ser publicados manualmente, pois o conector atual não expõe escrita de tags/releases.

## Branch de desenvolvimento

Todo trabalho novo da V1.1 deve ocorrer em `develop/v1.1`.

Não alterar `release/v1.0.0` para implementar melhorias, experimentos ou correções da V1.1.

## Regras do ciclo

1. Preservar compatibilidade com dados da V1.0.0.
2. Não reintroduzir sidebar + bottom navigation simultâneas.
3. Não reintroduzir hamburger/drawer legado.
4. Não criar versões paralelas de shell, componentes ou navegação.
5. Alterações globais devem ser feitas na base compartilhada.
6. Cada mudança deve passar por ALTERAR → SALVAR → VALIDAR.
7. Mudanças que afetem layout devem passar pela auditoria desktop + iPad/tablet + celular.
8. Mudanças que afetem dados, concurso, edital, mapas ou planejamento devem repetir o fluxo operacional de novo concurso.
9. Mudanças em PWA/cache/offline devem passar pelo smoke test real de PWA.
10. Evitar quebra de URLs, localStorage, backups, contestId e identificadores dos mapas.

## Gate obrigatório para futura V1.1.0

Antes de promover a V1.1.0:

- validadores estáticos sem erros;
- auditoria visual/funcional sem regressões;
- fluxo de novo concurso aprovado;
- smoke PWA aprovado;
- ausência de temporários, backups e legado comprovadamente morto;
- documentação e release notes atualizadas;
- commit final congelado antes da tag.

## Pendências herdadas

- Publicar manualmente a tag/release oficial `v1.0.0` no GitHub.
- Conferir manualmente zoom real do Chrome em 80%, 125% e 150%, já que o ambiente headless não reproduziu esse comportamento de forma confiável.

## Escopo funcional da V1.1

O escopo auditado está em `docs/V1.1_BACKLOG.md`.

A ordem aprovada para o ciclo começa por segurança dos dados e sincronização, seguida pela consolidação/auditoria dos mapas de estudo, performance, confiabilidade offline, observabilidade e somente depois evolução da automação interna.

Nenhuma funcionalidade nova deve ser adicionada apenas para “encher” a V1.1.

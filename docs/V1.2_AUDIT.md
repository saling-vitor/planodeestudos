Data da auditoria: 2026-09-26.

- SHA congelado: `79da5bfe2f486da208b6e04a3fc06e13eae9a54d`;

## Capacidades que já existem e não devem ser reconstruídas

### Novo concurso por edital

O fluxo atual já aceita PDF, valida arquivo, executa análise automática quando disponível, permite revisão manual dos dados extraídos, armazena o edital localmente e cria concurso + schema + blueprint de estudos.

Arquivos centrais:

- `assets/js/pa-contest-import-v01.js`;
- `assets/js/pa-edict-parser-v01.js`;
- `assets/js/pa-edict-flow-v01.js`;
- `edital.html`.

### Planejamento por disponibilidade

`planejamento.html` já permite configurar disponibilidade por dia, duração de bloco e distribuição do tempo entre mapa, questões e revisão. O plano só é gerado com disponibilidade mínima válida e respeita pesos/estrutura do edital.

### Mapas HTML diretos no Portal

`biblioteca.html` + `pa-study-blueprint-v01.js` já oferecem:

- importação direta de HTML;
- armazenamento local em IndexedDB;
- contrato H2 de importação;
- auditoria H3;
- validação de concurso/mapa/assinatura do blueprint;
- bloqueio da ativação quando a auditoria falha;
- ativação direta na Biblioteca e no Planejamento quando aprovada.

Conclusão: V1.2 não deve criar fluxos paralelos para concurso, disponibilidade ou importação de mapas.

## Achados

### A-01 · P0 · V1.2 sem CI automático

`.github/workflows/validate-v11.yml` dispara apenas em:

`develop/v1.1`

A branch `develop/v1.2` possui **0 execuções de workflow** até esta auditoria.

Risco: uma futura alteração funcional na V1.2 pode ser enviada sem passar automaticamente pelos validadores, Data Safety, auditoria dos mapas, cold-offline e auditoria de layout.

**Critério de correção**

Antes de qualquer feature V1.2, todo push em `develop/v1.2` deve disparar um gate de desenvolvimento completo e verde.

### A-02 · P0 · CI de desenvolvimento ainda acoplado ao RC da V1.1

O workflow `Validar V1.1` executa também:

- `validate_release_qa.py`;
- `validate_release_candidate.py`.

Esses validadores são artefatos do fechamento da V1.1 e não devem ser requisito de cada commit comum da V1.2.

**Critério de correção**

Separar:

- gate de desenvolvimento contínuo;
- gate de Release Candidate;
- gate de release final.

Os artefatos V1.1 permanecem preservados como histórico.

### A-03 · P1 · Metadados estruturados da V1.1 ainda indicam preparação

`data/version-contract.json` ainda contém:

- `targetRelease: 1.1.0`;
- `candidateRelease: 1.1.0-rc.1`;
- `releaseStatus: final-preparation`;
- referência ao Gate V1.1 Release #1 / SHA pré-final.

Entretanto, a V1.1.0 já foi publicada no SHA final `79da5bfe...`.

Isso não é bug de runtime atual, mas é uma inconsistência da fonte de verdade para o próximo ciclo.

**Critério de correção**

Marcar a baseline 1.1.0 como `released`, registrar o SHA final e não transformar os artefatos RC1 em estado ativo da V1.2.

### A-04 · P1 · README de produção está desatualizado

`README.md` informa:

`Release atual: 1.0.0`

A produção real é **1.1.0**.

**Critério de correção**

README deve refletir a release pública e o SHA/baseline vigente sem alterar o comportamento do Portal.

### A-05 · P1 · Workflow de deploy duplica versão PWA

A versão PWA 19.4 aparece em mais de uma fonte:

- `assets/js/pa-pwa-v01.js`;
- `service-worker.js`;
- `scripts/build_offline_pack.py`;
- `data/version-contract.json`;
- `.github/workflows/pages.yml`.

No deploy, `pages.yml` monta explicitamente `19.4-<sha>`.

Risco: futura alteração do contrato PWA pode deixar o deploy divergente do runtime.

**Critério de correção**

O deploy deve derivar a versão-base de uma fonte canônica validada, sem número PWA duplicado no YAML.

### A-06 · P2 · CSS compartilhado dos mapas ainda é muito complexo

Medição pós-V1.1.0:

- `study-map-shared-v01.css`: **581.558 caracteres**;
- `!important`: **9.341**;
- blocos `@media`: **240**.

A V1.1 removeu camadas mortas e melhorou performance, mas a folha continua grande e com alto custo de manutenção.

Não há evidência atual de regressão visual: a matriz dos mapas e o release gate estão verdes. Portanto, não é motivo para reescrita imediata.

**Critério para qualquer nova consolidação**

Somente refatoração comportamentalmente equivalente, com redução mensurável e aprovação integral da matriz real de mapas.

### A-07 · P2 · Páginas centrais ainda concentram muito JS inline

Medição aproximada da fonte:

| Página | Tamanho | blocos script |
| --- | ---: | ---: |
| `index.html` | ~91,9 KB | 20 |
| `configuracoes.html` | ~91,1 KB | 16 |
| `biblioteca.html` | ~31,8 KB | 14 |

Isso não é bug por si só. É dívida de manutenção: mudanças futuras podem ficar mais difíceis de testar e reutilizar.

**Critério**

Extrair apenas lógica comprovadamente compartilhada ou estável; não fazer reescrita ampla de páginas sem ganho mensurável.

### A-08 · P2 · Nomes de CI e artefatos continuam presos à V1.1

Ainda existem nomes como:

- `validate-v11.yml`;
- `rc-gate-v11.yml`;
- `release-gate-v11.yml`;
- `runtime_automation_v11.py`;
- artefatos `v11-qa-*`.

Eles são válidos como histórico, mas não devem obrigar a V1.2 a copiar toda a infraestrutura com nomes novos a cada ciclo.

**Critério**

O gate de desenvolvimento futuro deve ser estável/genérico onde fizer sentido, mantendo gates de releases históricas imutáveis.

## Classificação

### Bugs / inconsistências confirmadas

- A-01: ausência de CI automático para `develop/v1.2`;
- A-02: desenvolvimento acoplado ao RC V1.1;
- A-03: estado estruturado da release ainda em `final-preparation`;
- A-04: README informa release antiga.

### Dívida técnica confirmada

- A-05: versão PWA duplicada no deploy;
- A-06: complexidade residual do CSS dos mapas;
- A-07: concentração de lógica inline nas páginas principais;
- A-08: infraestrutura de CI nomeada por ciclo.

### Bugs funcionais do usuário

Nenhum bug funcional novo foi comprovado nesta auditoria. A produção V1.1.0 foi publicada com todos os gates verdes.

## Regra para a V1.2

Nenhuma feature nova deve começar enquanto A-01 e A-02 não estiverem resolvidos.

A V1.2 começa por tornar o processo seguro; depois avança para manutenção técnica e, somente então, para melhorias de produto observáveis.
